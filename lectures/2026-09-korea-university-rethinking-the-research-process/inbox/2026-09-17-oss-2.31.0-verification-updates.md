## 1. The surfaces we actually work in, and the ones we do not

The talk should say plainly where this work happens, because the audience will assume a chat window.

We work in **agents**, not chatbots. Concretely that means Claude Code and Codex, and mostly in the
**CLI**. The deck should define what a CLI agent is for an audience that has not used one: a model
with tool access running in a terminal, in a repository, able to read and write files, run code, and
call other programs, under permissions the user sets.

The same skills work in the **desktop and IDE applications** of both tools. That is worth stating so
nobody thinks a terminal is required.

They are **not advisable in chatbot interfaces**, and this should be said carefully. They probably do
work in some form. I cannot confirm it, because I do not work that way, and the talk should not
claim otherwise. The honest framing is that the verification story depends on the agent being able to
run code and read a repository, which a chat window does not do.

## 2. What shipped today, and why it matters to this talk

Released Open Science Skills v2.31.0. Claude 43 skills, Codex 42. Four things bear on verifiability.

### The reading-versus-running distinction

This is the sharpest idea to come out of the session and I think it belongs in Part 2.

Before today, nothing in the library executed anything against a research artifact. An audit found
zero occurrences of `lintr`, `styler`, `ruff`, `pytest`, `testthat`, or `sha256` across all skills.
`replication-package` graded a package by reading it, and its own checklist item "the package runs in
a clean temporary directory" was a human checkbox that nothing ever tested.

The failure this permits is worth a slide. `paper-review-lite` runs nine agents over a manuscript and
every one of them reads. Its Numbers agent compares the abstract against the tables, so it catches an
abstract saying 0.34 against a table saying 0.31. It cannot catch a table saying 0.31 when the code
now produces 0.28, because you changed the model spec, re-ran, and updated the figure but not the
table. Both documents agree with each other. Both are wrong. The truth is not in the manuscript, so
no amount of careful reading reaches it.

That is the argument for execution-based verification, and it is concrete enough to land.

### `verify_package.py`

New bundled script in `replication-package`, in two tiers.

The **static tier** reads files only, costs nothing, takes about a second: is a seed set, is session
or environment information recorded, is there a dependency lockfile, does any absolute path point at
someone's home directory, is anything credential-shaped committed, plus a sha256 manifest of the data
directory.

The **execution tier** copies the package to a temporary directory, runs its master script there, and
compares what appeared against the figure-table crosswalk. The interesting check is the last one. A
package can run cleanly and still fail to produce a table it claims to produce.

Execution is off by default and requires explicit authorization, because it runs code the package's
author wrote. On Claude that authorization is a real prompt, not a sentence in a paragraph, since a
clean-room run can take half an hour and a question buried in prose is easy to scroll past.

Worth saying in the talk: the first run against an existing project will often fail for reasons that
are not bugs, such as data living outside the repo or a package installed by hand years ago. That is
the check telling you the analysis was never portable, which is itself the finding.

### `paper-review-lite` should be in the deck

It currently appears nowhere in the planning wiki and that is a gap. It is the pre-submission review
most people would actually reach for, and as of today its orientation step runs the static checks
automatically and hands the output to the Numbers agent and the Replication Archive agent as
evidence. That is the fix for the blind spot described above: the agent finally has something outside
the manuscript to compare against.

There is also a new `/oss:verify` alias that runs the checks alone, without the grading or the FAIR
audit. That is the one to run after a work session rather than before a submission.

### `sitrep` and `finished`

Two new skills under a new Repo Hygiene category, on both platforms. `sitrep` reports where a project
stands by reading whatever handoff and log files the repo keeps and checking live git state, and
flagging where the documents and the repository disagree. `finished` records what changed back into
those files at session close, separating verified work from work merely attempted.

These fit the talk's continuity theme rather than its verification theme, but they are the answer to
"how does the next session know what happened." One detail is presentation-worthy: `sitrep` explicitly
distinguishes committed from verified, because they are not the same claim.

## 3. Two smaller points that may be useful

**Every skill is now on demand.** None loads from context, none is suggested unprompted. An idle
session carries none of the library instead of roughly 10k tokens. If the talk touches context
economics, this is a clean worked example of a real tradeoff: a skill that fires on its own has to
earn its context in every session, and a specialist that fires rarely is cheaper to name than to
carry.

**We found the defect by looking, not by testing.** The release began because the slash-command menu
showed one skill twice. The cause was that the package check had been asserting the wrong invariant
for months, enforcing the duplication rather than catching it. If the talk wants a self-deprecating
example of why you verify your own tooling and not just your results, this is it, and it is true.
